# Asobi 0.8 implementation plan

Status: approved design; WP1 and WP2 merged. Owner: tech lead (TL). Implementers: one agent per work package (WP).

## What 0.8 is

One breaking release that:

1. removes skills management ([ADR 0004](../decisions/0004-remove-skills.md));
2. replaces sessions with tasks and abandons idle tasks automatically ([ADR 0006](../decisions/0006-tasks-replace-sessions.md));
3. starts a clean schema baseline and refuses pre-0.8 graph files ([ADR 0007](../decisions/0007-clean-schema-baseline.md));
4. adds a shared server, `asobi serve`, with named graphs and an HTTP remote mode that falls back to the local graph when the server is unreachable ([ADR 0005](../decisions/0005-remote-server.md)).

The ADRs are the specification. Where this plan and an ADR disagree, the ADR wins and the TL fixes the plan. Vocabulary is in [`CONTEXT.md`](../../CONTEXT.md); use its terms (graph, workspace, server, graph name, local/remote mode, task, epic, abandoned) in code, docs, and commit messages.

## How agents work

### Before starting a WP

Read, in order: `AGENTS.md`, `CONTEXT.md`, the ADRs your WP implements, then this plan's section for your WP. Do not start a WP whose dependencies are not merged into the integration branch.

### Branches and checkouts

- Integration branch: `feat/0.8-serve-drop-skills`. Only the TL merges into it.
- Work directly in the vendored checkout, `vendor/asobi/` in harus-workstation. No git worktrees.
- Each WP gets its own branch from the current integration branch:

  ```bash
  git -C vendor/asobi switch -c wp<N>-<slug> feat/0.8-serve-drop-skills
  ```

- One checkout means one writer: only one agent works in `vendor/asobi/` at a time. Start a WP only when the checkout is clean and on the integration branch, and leave it that way after your final commit (`git switch feat/0.8-serve-drop-skills`), so the TL can review your branch from the same checkout.
- Commit freely on your WP branch with conventional commits (`feat:`, `fix:`, `docs:`, `test:`, `chore:`). Never push, open a PR, publish, tag, or release. The TL asks the owner for every remote action.

### Definition of done for every WP

- Every acceptance criterion in the WP is met and each is covered by a test or a stated manual check.
- `make check` passes on the WP branch.
- Docs that the change makes false are fixed in the same WP (see "Where the answers actually live" in `AGENTS.md`).
- No scope beyond the WP. Anything found outside it goes in the report, not the diff.
- The WP ends with a report to the TL: branch and head commit, what changed, how each criterion was verified (happy path, edge cases, failure paths — not just a test count), anything deferred, and anything in this plan that turned out wrong.

### Review (TL)

The TL reviews each WP branch against its criteria and the ADRs, runs `make check` on it, and merges with `--no-ff` into the integration branch, or returns findings to the implementer. Review checklist:

- The diff matches the ADR, not a reinterpretation of it.
- Commands still depend on `api` traits only; provider details stay under `src/storage/`.
- Tests exercise failure and edge paths, and isolate with a temporary `ASOBI_DATABASE_URL`.
- No new dependency without the reason recorded in the commit message; no async runtime.
- Docs and `CHANGELOG.md` (Unreleased) updated where behaviour changed.

                    │                                 ├──► WP4 server ──┐

The graph shows logical dependencies. Because there is one checkout and one writer, WPs run one at a time in this order: WP1, WP2, WP2b, WP3, WP4, WP5, WP6, WP7, WP8. WP2b was added after WP2's review and sits on the WP2 → WP4 path. (WP2/WP3 and WP4/WP5 are independent of each other, so their order within each pair may swap if it helps.)

WP1 goes first alone because it deletes about half of `src/` and touches `lib.rs`, `commands.rs`, `dispatch.rs`, `paths.rs` and the test suite, which every later WP would otherwise conflict with.

## WP2: Tasks replace sessions; idle tasks are abandoned

Implements ADR 0006. Depends on: WP1.

### Scope

- `src/storage/sqlite.rs`: remove `"session"` from `PURGEABLE_ENTITY_TYPES`; update the retention doc comment ("finished session or task").
- `src/compact.rs`: drop `"session"` from the excluded types.
- Add the abandonment sweep in `src/storage/sqlite.rs`:
  - Candidates: `entity_type = 'task'`, status non-terminal (not `DONE`/`CLOSED`/`ABANDONED`) or absent, `last_activity` older than `abandon_days`, and no `part_of` child that is itself open.
  - Effect, in one transaction per sweep: set `status = ABANDONED` and append the observation `abandoned automatically after <N> idle days`.
  - Reuse the existing `last_activity` expression (the retention candidate query); do not introduce a second definition of activity.
- Settings: `abandon_days` in `AsobiConfig`, env `ASOBI_ABANDON_DAYS`, default 7, `0` disables. Resolve exactly like `retention_days` (env, then `asobi.toml`, then default).
- Order inside the sweep: **abandon first, then retention.** Abandoning appends an observation, which refreshes `last_activity`, so a newly abandoned task survives retention for its full window (the two-step lifecycle in ADR 0006).
- Refactor `sweep_expired_once` so the sweep body is a public inherent method on `SqliteStore` (e.g. `sweep(&self) -> ApiResult<SweepReport>`), still called once per process before the first write in local mode, and callable repeatedly by WP4's server thread. It is not part of the `v2` traits and not an RPC method.
- Docs: `docs/usage.md` (task lifecycle, `abandon_days`, `ASOBI_ABANDON_DAYS`), `AGENTS.md` retention trap (it now also abandons), `CHANGELOG.md`.

### Acceptance criteria

Tests seed timestamps directly (mark the file `// storage-boundary: provider-test`) and disable or set windows explicitly:

- An open task idle past `abandon_days` becomes `ABANDONED` with the observation; a task active within the window is untouched.
- A task with no status, idle past the window, is abandoned.
- An epic with an open `part_of` child is not abandoned even when its own entity is idle; once every child is terminal and the epic is idle, it is.
- `abandon_days = 0` (config and env) disables abandonment; retention still runs.
- A task abandoned by the sweep is not deleted by retention in the same sweep, and is deleted once `retention_days` pass.
- Entities of type `session` are no longer purged by retention (regression test).
- `make check` passes.

## WP2b: Clean schema baseline

Implements ADR 0007. Depends on: WP2.

### Scope

- `src/storage/sqlite.rs`:
  - `SCHEMA_VERSION = 9`. A new file (`user_version = 0`) is created at 9, keeping `PRAGMA auto_vacuum = INCREMENTAL` before the first write.
  - Delete `upgrade_to_v5`, `upgrade_to_v6`, `upgrade_to_v7`, the v8 `DROP TABLE asobi_truth_fts` step, the post-upgrade FTS `rebuild` calls that only existed for upgrades, and their doc comments.
  - `open_at`: a non-zero `user_version` other than 9 returns an error naming the path, stating the file predates 0.8 (or is newer, for a higher version), and telling the user to move it aside. The file is not modified: check before any `PRAGMA` that writes (journal mode included).
  - `asobi_entities.updated_at` → `last_activity` (`NOT NULL DEFAULT CURRENT_TIMESTAMP`). Triggers set it to `CURRENT_TIMESTAMP` after insert, update and delete on `asobi_observations` and `asobi_truths` for the affected entity. Relations do not count.
  - Replace `LAST_ACTIVITY_SQL` with `e.last_activity` in the retention and abandonment queries; delete the constant.
- Tests:
  - delete the pre-v5 migration test in `tests/backend_api_contract_test.rs` and any other old-file upgrade test;
  - keep the incremental-vacuum test (a new file's property);
  - the `age()` helper in `tests/sweep_abandonment_test.rs` must set `last_activity` **last**: its updates to observations and truths fire the new triggers and would reset it to now.
- Docs: `CHANGELOG.md` (breaking: pre-0.8 files refused, move aside; schema 9), `docs/architecture.md` if it describes the schema or migrations, `AGENTS.md` if a statement becomes false.

### Acceptance criteria

- A new database has `user_version = 9`, `auto_vacuum = INCREMENTAL`, and an `asobi_entities.last_activity` column; no `updated_at` on entities.
- Opening a file with `user_version = 8` (and one with `10`) fails with the path and the move-aside instruction, and the file's bytes are unchanged afterwards (compare before/after).
- `last_activity` moves on observation add/edit/delete and truth upsert/delete, and does not move on relation create/delete (one test per case).
- All WP2 sweep tests pass unchanged in intent (only the `age()` helper adapts).
- `rg -n "upgrade_to_v|mcp_|libsql|chunks" src` finds nothing.
- `make check` passes.

## WP3: RPC contract (types and error mapping only)

Implements the "RPC contract" section of ADR 0005. Depends on: WP1. No networking in this WP.

### Scope

- New module `src/rpc.rs` (or `src/rpc/`): one params type per method in ADR 0005's table, a method-name enum or constants, and the error body `{kind, message}`. No envelope.
- Add `Serialize`/`Deserialize` (camelCase) to `ObservationInput`, `ObservationDeletion`, `OpenNodes`, `SearchQuery` so they travel as params. `SearchQuery.filters` serializes as `[key, value]` pairs.
- `ApiError` ↔ HTTP status and `kind` as in ADR 0005's error table, plus the protocol cases (`unknownMethod` 404, `badRequest` 400/405). The mapping lives here as data (status as a plain number), so WP4 and WP5 use it whatever HTTP library they pick.
- A dispatcher function that is transport-free: given a method name, the raw params JSON, and a `&(impl GraphStore + SearchStore + MaintenanceStore + TaskStore)`, call the trait method and return either the result JSON or the error (status, body). `maintenance.reset` always returns the `unsupported` error. `server.hello` returns `BackendInfo`. WP4 wraps this in HTTP; keeping it transport-free is what makes it unit-testable here.
- `asobi schema`: publish the new param types (see `docs/response-contract.md` for how schemas are exposed).

### Acceptance criteria

- Round-trip test for every method: params serialize → deserialize → dispatcher → result serializes, against a temporary `SqliteStore`.
- Every `ApiError` variant maps to its status and `kind` and back to the same variant.
- Unknown method → 404 `unknownMethod`; malformed JSON and wrong params shape → 400 `badRequest`.
- `maintenance.reset` returns the `unsupported` error and leaves the graph intact.
- `make check` passes.

## WP4: `asobi serve`

Implements ADR 0005 "Server behavior" and graph naming. Depends on: WP2, WP3.

### Scope

- Library: choose a synchronous HTTP server crate (candidate `tiny_http`) after reading its docs; record the choice and reason in the commit message. No async runtime.
- `asobi serve --listen <addr:port>` subcommand. Data directory: the resolved `data_dir`; each graph is `<data_dir>/<name>.db`.
- Route: `POST /rpc/<graph>/<method>` into WP3's dispatcher. Non-`POST` → 405; paths outside `/rpc/` → 404.
- Graph names must match `^[a-z0-9-]+$`; otherwise 422 `invalid`, and no file is touched. An unknown valid name is created on first use (opening a `SqliteStore` at that path).
- Keep opened stores in a registry (`name → SqliteStore`), opened lazily.
- One request at a time: a single accept loop handling each request to completion.
- Background sweep: a thread that, every hour, takes the same lock as request handling and calls WP2's `SqliteStore::sweep` on every graph in the registry and every `*.db` in the data directory. Sweep failures are logged and never stop the server.
- Retention and abandonment settings come from the server's own config and environment.
- Logging to stderr via the existing tracing setup: one line per request (graph, method, duration, error kind).
- Docs: `docs/usage.md` (`serve`, flags, route, graph naming, tailnet-only warning), `CHANGELOG.md`.

### Acceptance criteria

- Integration tests start the server on `127.0.0.1:0` in-process and call it over real HTTP with a minimal client:
  - two graph names are isolated from each other; a new name creates `<name>.db`;
  - `../x`, `A`, and empty names are rejected and create no file;
  - `maintenance.reset` is refused;
  - a request arriving during a sweep completes correctly after it (no interleaving);
  - the sweep runs on demand in tests (expose an interval or a trigger for tests; the production interval is one hour).
- `make check` passes.

## WP5: Remote client, configuration, fallback

Implements ADR 0005 "Shape", "Data placement" and "When the server is unreachable". Depends on: WP3.

### Scope

- Library: a synchronous HTTP client with HTTPS support (candidate `ureq` with rustls); record choice and reason in the commit message. The server is reached at `https://asobi.h.azusachino.com` in production.
- Configuration: `remote` and `graph` in `AsobiConfig`; `ASOBI_REMOTE`, `ASOBI_GRAPH` override them; `graph` defaults to `asobi`.
- `RemoteStore` implementing the four `v2` traits by one RPC per call via WP3's types; errors mapped back to the same `ApiError` variant.
- Storage selection: replace `pub type Storage = SqliteStore` with a type that is either local or remote and implements the traits by delegation; `AsobiRuntime::open_default` chooses from config. Commands stay unchanged.
- Connections: one HTTP client per process, reused for `server.hello` and every call, so a command pays the TCP and TLS handshake once (HTTP/1.1 keep-alive). HTTP/2 is not a goal: each command is a short sequence of calls from a fresh process, with nothing to multiplex.
- Handshake: `server.hello` once per process, before the first call; `apiVersion` mismatch is a hard error (not a fallback).
- Fallback: connect timeout ~2 s. If the server is unreachable at handshake, warn on stderr — every command — that the command is running against the local graph and its writes will not reach the server, then use the local `SqliteStore` for the rest of the process. A transport failure after a successful handshake is an `Unavailable` error for that call (no mid-command switch, so one command never splits its writes).
- `observation_limit` stays client-side; `compact` writes to the local `topics_dir` in both modes.
- Docs: `docs/usage.md` (`remote`, `graph`, env vars, fallback and its warning), `CHANGELOG.md`.

### Acceptance criteria

Unit-level in this WP (full server tests are WP6):

- Config resolution: file only, env only, env over file, `graph` default `asobi`, no `remote` → local mode.
- With `remote` pointing at a closed port: the command succeeds against the local graph, prints the warning, and completes within ~2 s plus normal runtime.
- A server answering `hello` with a different `apiVersion` → the command fails with a clear error and writes nothing anywhere.
- A command making several calls opens one connection (test against a local server that counts accepted connections).
- Local mode behaviour and output are byte-identical to 0.7.3 for the existing CLI tests.
- `make check` passes.

## WP6: End-to-end verification

Depends on: WP4, WP5.

### Scope

- Run `tests/backend_api_contract_test.rs` and `tests/concurrency_test.rs` against remote mode (in-process server on `127.0.0.1:0`, client configured via `ASOBI_REMOTE`/`ASOBI_GRAPH`) in addition to local. SQLite-only cases (migrations, `sqlite_master`, incremental vacuum) stay local-only.
- End-to-end CLI tests: two "devices" (two temp workspaces) sharing one graph see each other's writes; a third on another graph does not.
- Fallback end-to-end: stop the server mid-suite; next command warns and uses local; restart; next command uses remote again, and the outage write is absent remotely (documenting the accepted loss).
- Abandonment through the server: seed an idle task via the server's store, trigger the sweep, observe `ABANDONED` over RPC.
- Benchmark sanity: run `make bench-tasks` locally and against remote once; record numbers in the report (no threshold).

### Acceptance criteria

- All of the above pass under `make check`; concurrency test passes in remote mode with the same process count as local.
- Findings that point to a bug in WP2–WP5 go back to that WP's branch, not patched here.
- `tests/backend_api_contract_test.rs` compiles with two unused-import warnings (`std::fs`, `std::path::PathBuf`) that predate 0.8; remove them while reworking the file.
